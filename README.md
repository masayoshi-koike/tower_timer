## 1. サービス概要

「TOWER TIMER」は、ポモドーロタイマーの経過時間とともにピクセルアートの建物が積み上がる、自動記録型の学習管理アプリです。  
タイマーと連動した視覚的な成長と、日々の学習時間の自動蓄積により、  
建物の完成と共に自分の努力の軌跡をひと目で実感できます。  
 
---

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

独学でプログラミング学習を始めた際、継続とモチベーション維持に苦労した経験から、  
学習記録アプリとポモドーロタイマーを取り入れました。これにより学習の密度は高まったものの、  
自身が使用していた既存のアプリには2つの課題を感じていました。  
  
***1 学習記録アプリの機能過多 : 初回の教材設定や細かな時間分類など、記録すること自体の手惑い（認知負荷）が大きく、継続の妨げになる。***  
***2 ポモドーロタイマーの無機質さ : 視覚的な情報が遮断されすぎているため、作業を始める・続けるための「楽しさ」に欠ける。***  
 
---

### 2-2. なぜそれが問題なのか

これらの2つは「機能過多」「シンプルなデザイン性」という、一見`相反する要素`のように感じますが、  
「ユーザーが学習を始める・続けるための`『心のハードル（認知負荷）』`を上げてしまっていること」   
という共通の問題があると考えます。  

---

### 2-3. この問題に対するアプローチ

ポモドーロタイマーは、勉強を始めるための「最初の一歩」のハードルを下げる役割です。  
だからこそ、触りたくなる楽しさ（変化するアニメーション）が必要になると考えました。  
そのため、細かい内訳ではなくトータル時間がわかりやすいUIを目指して、  
始める時は楽しく、振り返る時はシンプルに迷わない、というメリハリをつけたアプローチを考えています。  

---

## 3. 課題の整理（表面的になっていないか）

### 3-1. 表に見えている困りごと

***使い続ける楽しさという「視覚的なUI/UXの少なさ」と「ユーザーの現在地」が直感的にわかりずらい***

---

### 3-2. 本当に解決したい課題は何か


- 視覚的: 「始めるための楽しさ」をUIの視点で解決したい。  
- 機能的: 「続けるためのシンプルさ」をUXの視点で解決したい。  

→ 本当に解決したい課題 ： 「学習」体験を支えるアプリケーションに発生する、`本質的ではないコスト`の課題を取り除く。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

年齢設定 :
  - 年齢 : 25 ~ 35歳  
  - 理由 : リスキリングや自己学習を行う割合は比較的上記の年齢層が多く、  
  また学習にコミットできる学生よりも、社会に出て仕事とは別で学び直しをしたいユーザーを想定しています。 

  
生活・状況設定 :  
  - 職業 : アパレル勤務(ECサイト運営)

[生活の流れ]  
朝8時に起床。9時に家を出て職場まで電車移動(電車:40分)。移動中は読書をしている。  
10時から始業開始で残業は無く、自宅には20時に帰宅。  
週2日(仕事終わりと休日)ジムへ通い適度に運動をしている。  

[休日の流れ]  
休日は自宅で過ごすことが多く、趣味の映画鑑賞や読書をして過ごすことが多い。  
また仕事で携わった動画制作に興味があり、1日30分~1時間ほど動画編集の勉強をしている。  

[現状の課題]  
リスキリングの意欲や日常的に行動を起こすことは苦手ではないが、  
独学で広く浅く学習をしてしまうため、長期的で継続した学習に苦手意識がある。  
また、継続的に1時間以上の学習を進めることを目標としたい(理想は平日1~2時間/休日3~4時間の学習)  
  
  - 理由：1日の大半を仕事にコミットするのではなく、自主的な学習を仕事に活かそうと考えているユーザーを想定しているためです。  


環境設定：
  - 環境：平日の夜（21:00〜）および休日の自宅。学習にはPC（動画編集用）を使用し、タイマーを起動。  
  - 理由：残業がないとはいえ仕事の疲労もあるため、PCを開いてから1時間を超える学習モードを維持するハードルが高い環境です。  
そこで、建築物が積み上がっていく視覚的な成長と楽しさによって、とりあえずスタートを押してみるというハードルを下げ、  
また、危機感で無理やり勉強させるのではなく、「せっかくならもうちょっとだけタイマーを回して、建物を完成させちゃおう」と思わせるような、  
少しのゲーミフィケーションと視覚的な達成感が良いと考えています。
---

### 4-2. 自分とユーザーの距離

- 過去の自分

社会人になり改めて学習をする「過去の自分」は、学習内容の選定/学習を支える教材/新しい分野におけるインプット過多  
などにより、学習継続へのコストがすでに高まっていましたが、その中でも継続して学習を進められていたのはポモドーロテクニックと  
今までの学習記録を振り返ることによるモチベーション維持でした。   
この2つの方法に出会った際、これらを紹介する動画メディア・ブログ記事やウェブサイト記事の多さから、  
自身の課題と同じ問題に直面しているユーザーが多いことに気付き、この視点がユーザーとの距離として近いと考えました。  

### 4-3. 実際に使われる可能性について(需要・存在確認)

このアプリケーションは、これから独学で学習を始めようと考えているユーザーが、  
***ポモドーロタイマーや学習記録アプリの導入を悩んでいるシーン***を想定しています。  
そして、そのアプリケーションの選定の段階で、`機能が充実しているアプリ`を検討しているのではなく、  
始めやすい導線(スタートまでのインターフェースのわかりやすさ・少しでも始めようと考える動機/面白さなど)と、  
振り返りやすいシンプルな機能を求めているという、  
「導入のハードル」で迷っているユーザーにアプローチをしたいと考えています。  

## 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

このアプリケーションまでの動線の想定として、  
1. 自主学習をスタートしたが、うまく継続や集中した学習ができないと考えている。  
2. 「おすすめ学習法」などの検索をしたユーザーがポモドーロテクニックの存在や、学習記録によるメリットを認知する。  
→様々な検索タイトルで確認をしたところ、広い割合で「ポモドーロテクニック」が上位にヒット、  
また、モチベーション維持での学習記録のメリットが記述されている。  
3. ウェブサイトで「ポモドーロタイマー」と検索をして、上位にヒットしたアプリケーションを試す、計算した時間をメモしていったが、  
トータルの時間を記録したいため、学習記録アプリも導入。  
4. 2つのアプリケーションを併用するデメリットが大きいため、両方の機能を兼ね備えたアプリケーションを選定する。  
5. ペルソナ設定をしたユーザー層からのサービス導入

### 5-2. それでも自分が作りたい理由

上記の既存サービスなどを使用する中で、  
勉強を推進しているアプリケーションではありますが、  
提供されている機能が ***「学習に慣れ親しんでいる」という想定*** で設計されているように感じました。  
今現在の自分の視点では、独学での学習に抵抗感は無いため機能が豊富である点のメリットは感じられますが、   
学習スタート時点ではその豊富さに疲れてしまう、また導入のハードルが高いと考えています。  

### 5-3. 差別化を「体験価値」で表現する

今回のアプリケーションは***学びに慣れ親しんだユーザー***へ向けた、機能の豊富さによる充実感あるアプリケーションではなく、  
独学で学習をしているユーザーが`「とりあえず始めてみよう」`となる体験に重視して差別化を図りたいと考えています。  
中々継続した学習ができないユーザーの学習へのハードルを下げることを目的として、  
ピクセルアートの成長を感じる視覚的な体験と、  
継続していきたいと考える学習記録の積み重ねを提供できると考えます。  

UI視点での成長を感じられる視覚的体験:   
ゲームのような楽しさではなく、タイマーをスタートさせるためのハードルを下げる視覚的な楽しさと、学習が身になるという実感です。  
分かりやすく学習時間が積み重なっていく体験：  
どの教材を何時間学習したのか/教材毎のパラメーター/学習時間によるグラフ遷移   
これらの機能は後から付随するものであり、今回のアプリケーションが重要視するのは「積み重ねた時間」が分かりやすいことです。

## 7. このアプリで実現すること

### MVPで作る機能

・ログイン機能(新規登録/ログイン/ログアウト)  
：ポモドーロタイマーをとりあえず使いたいという、今回のアプリのメインである学習ハードルを下げるという観点から、  
ユーザー登録は必須にしない予定です。  

・学習記録機能(ログイン後使用可能)  
：MVPではトータルの学習時間の確認のみの予定です。  

・ポモドーロタイマー機能  
：MVPでは25分の学習と5分の休憩の時間固定(スタート/ストップボタンのみ)

・タイマーの経過で変化するアニメーション  
:フェードインでの変化やスプライトシートの作成で繰り返し動くアニメーションの実装

### 本リリースで作る機能

・学習記録機能の拡張(ログイン後使用可能)  
：1日毎/月毎の学習時間の確認  
：カレンダー方式(またはそれに類似した日付を枠線のみで表現したわかりやすいデザイン)のUIの実装   
***※ただし、今回のアプリケーションは積み上げたトータル時間の分かりやすさを重要視しているため、機能として作成して、***   
***UIの優先的な見やすさは下げて画面構成をする予定です。***

・ポモドーロタイマーのセット数変更機能  
:セット数の追加(25分作業5分休憩を4セットなど)  
***※作業する時間を変える機能(5分毎に時間変更)も検討しましたが、ポモドーロテクニックを取り入れた学習法という点に重きを置いているため、***  
***現状は25分の設定を維持しようと考えています。*** 


・作業中のBGMの設定(ログイン後使用可能)   
:今回のアニメーションのデザインがピクセルアートのため、チップチューン風の効果音や、  
金槌の音、風の音などの環境音に近いBGMの設定を想定しています。

## 8. このアプリの懸念点とその対策

【懸念点1】  
このアプリケーションは建築物が成長することをメインのUIとしていますが、 
そもそも集中した学習に`視覚的な要素`はいらないのでは？という懸念点も考えられます。  

・上記の考え方は、学習にストイックなユーザーであれば合致し別のアプリケーションを選ぶため、  
そのユーザー層を掬い上げることは難しいと感じます。  
しかしながら、どれだけ集中に最適な無機質タイマーであっても、  
「アプリを開いてスタートボタンを押す」という最初の一歩を踏み出せなければ意味がありません。  
その少しのハードルをUIの建物の積み上がるビジュアル的な視点で少しでも解決できるのではと考えます。 

【懸念点2】  
学習の記録機能は豊富にあることで`幅広いユーザー層（ターゲット）`を獲得できるのではないか、  
という懸念点も考えられます。  

・この点に関しては、  
ユーザーが多機能設定を選択すること自体にエネルギーを使い、かえって行動を起こしにくくなる。  
また、自由な登録機能は「記録すること自体が目的化する」という本末転倒を生むのではという考えのもと、  
あえて機能を絞ることでユーザー体験を向上したいと思います。

## 9. 今後の展開・発展の方向性

今回は変化するピクセルデザインの建造物の種類が1種類のみですが、  
今後はデザインを拡充していき、ランダムでデザインが変わる仕様を検討しています。  
また、デザイン数次第で、建てた建築物のデザインを後々確認できる機能も考えていますが、  
この機能は`「わかりやすいインターフェース」`という優先するべき軸のズレに繋がる可能性がある為、  
現段階では優先順位は下げています。

【サービス使用後のデータ】  
サービスをスタートしてユーザーが増えることで、  
ユーザー同士の交流的なアプローチ(フォロワー同士の学習の共有)により、  
今回のアプリケーションの目的である「学習への取り組むハードル」を下げる効果なども期待できますが、  
わかりやすくシンプルなインターフェースを損なう要素が増える点は排除したいため。  
「機能を増やす」というアプローチが良いのではなく、  
「優れたUIに育て上げていく」というアプローチが適しているのではないかと考えています。  

### 今考えている発展案

- 機能追加の方向性：  
  ・優先度(高)：ピクセルデザインの種類増加  
  ・優先度(中~下)：ピクセルデザイン保存機能/フォロワー(友人登録？)交流機能  

- UI・体験の改善：  
  ・アプリケーションスタート前の使用方法などのUI  
  ・アプリ機能への動線を崩さない設定画面への動線   
  →MVPと本リリース時点でのメイン機能の実装次第ではありますが、アプリケーション使用時の使用方法の分かりやすさは、  
  アプリケーションをまず使ってみるか/使わないかの一番初めの壁になると考えるため、モーダルのみでシンプルにするのか、  
  機能毎に説明を入れるのかなど、細かく思考をして発展をさせるべき点だと想定しています。

- 機能以外の工夫：  
  ・変化するアニメーションは、あまりに忙しなく動くとデメリットになってしまうため、
  集中を保ちながらもふと目にした瞬間に変化が楽しめる線引きを重要視する予定です。

## 10. 技術スタック（手段としての技術）

### 10-1. 使用予定の技術

| カテゴリ | 技術 |
| --- | --- | 
| バックエンド | Ruby / Rails |
| フロントエンド | TypeScript / React / Inertia.js |
| データベース | PostgreSQL |
| 開発環境 | Docker |
| インフラ | Render |


- バックエンド選定理由  
：Railsの「設定より規約（CoC）」の思想により、初期セットアップやルーティング、データベース連携にかかる時間を大幅に削減できると考え、  
また、コア機能である「タイマーロジック」や「ビルの成長アルゴリズム」の開発にリソースを集中できる点がメリットであると想定しています。

- フロントエンド選定理由  
:Reactによる動的表現で、ポモドーロタイマーのリアルタイムなカウントダウンや、時間が到達した瞬間にビルが成長するアニメーションなど、  
状態（State）に依存する動的なUI構築において、Reactのコンポーネント指向がうまく機能すると考えました。

- データベース選定理由  
:Rails環境での親和性と実績が豊富であり、将来的な拡張性や信頼性に優れている。

---

### 10-2. 技術選定の比較検討

今回のアプリケーションでは、  
Railsをapiモードにして、フロントエンドをReactで分けた開発を検討していましたが、  
:モノレポ構成にしてホスティング先を1箇所にできる点  
:API サーバーを別に建てなくていい  
というスピーディーな開発が可能であるのではないかと考えと、  
また、ポモドーロタイマーの画面の変化量や、学習時間確認画面の画面の構成案から
